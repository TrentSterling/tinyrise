# PRIMARY PRODUCT VISION

The best description of the target is:

> **A modern architectural Townscaper-like city builder where large-scale city shaping transitions seamlessly into detailed buildings and tiny simulated lives.**

The desired hierarchy is:

**CITY SCALE**
→ districts / roads / properties / skylines

**BUILDING SCALE**
→ procedural façades, setbacks, bridges, courtyards, terraces, materials, stair access

**HUMAN SCALE**
→ residents, workers, deliveries, cafés, gardens, movement, routes, furniture interactions

The player should be able to zoom from:

> “I made this district.”

to:

> “That person walked across my bridge, used those stairs, sat in that chair, and drank coffee.”

That multi-scale relationship is one of the strongest unique directions the project discovered.

# DESIGN VALUES

## 1. Sandbox freedom comes first

Trent LOVES sandbox games.

Do not turn this into a punitive city-management spreadsheet.

Avoid immediately adding:

- taxes
- sewage
- crime
- police
- fire departments
- ten resources
- complicated zoning percentages
- rent micromanagement
- offline-idle grind
- arbitrary failure timers

The project has gameplay now, but the architectural toy must remain enjoyable without objectives.

---

## 2. Architecture should have consequences

The game became much better once construction affected simulation.

A bridge should alter routes.

A stair should genuinely connect floors.

Removing a bridge should genuinely isolate destinations.

A café should have capacity.

Residents should actually use chairs.

The visual architecture and simulation must tell the same truth.

THIS IS IMPORTANT.

We found multiple bugs where:

- stairs visually faced one direction but navigation ignored them
- residents effectively teleported through abstract routes
- cafés were “visited” without people using furniture
- routes technically existed but were visually unreadable
- furniture and stairs could overlap

Those kinds of visual/simulation mismatches are unacceptable.

---

## 3. Prefer visible problems over hidden stats

Good gameplay:

> “The café is visibly crowded.”

Good gameplay:

> “Everyone is using one stairwell.”

Good gameplay:

> “This garden lost access when I removed the bridge.”

Bad gameplay:

> “Efficiency rating -12%.”

Whenever possible, the player should understand problems by looking at the city.

Contextual overlays are allowed, but the world itself should communicate the state.

Reference architecture used:

# ABSOLUTE QA RULE

THIS IS THE MOST IMPORTANT PROCESS LESSON FROM THIS PROJECT.

## NEVER SHIP A BUILD WITHOUT RUNNING IT.

Several bad regressions occurred during development because work was:

* syntax checked
* reasoned about
* claimed as complete

without actually running the exact delivered HTML.

Bugs caught this way included:

* `applyPreset is not defined`
* blank renderer
* `hex.replace is not a function`
* broken startup
* missing hero assets after packaging
* route tracer that technically existed but was visually invisible
* cars snapping/driving sideways
* tree leaves floating away from trunks
* café sign geometry visibly broken
* car roof geometry visibly absurd

Therefore:

# Every substantial change must include:

1. open EXACT final HTML in Chromium
2. verify first rendered frame
3. check console
4. check WebGL errors
5. perform representative player actions
6. visually inspect screenshots
7. preferably inspect multiple camera angles
8. test desktop and mobile if UI changed
9. only THEN say it is done

A unit test is not a visual inspection.

A syntax check is not a playtest.

A mesh existing is not proof it looks good.
